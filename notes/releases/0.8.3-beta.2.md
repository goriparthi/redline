RedLine now keeps a diagnostics log of what went wrong, and a new `redline log` command reads it back.

### Added: a diagnostics log

Until now RedLine had no logging at all. There was no record of a failure anywhere, and around a hundred and thirty places in the code discarded errors silently, so a sidecar that stopped parsing or a config that failed to save left nothing behind to look at. The only way to investigate anything was to reproduce it live.

Events are written as one JSON object per line to `~/.local/share/redline/diagnostics.ndjson`. Each carries a UTC timestamp, a level, a stable code to group on, a message and a little context. The file is line oriented on purpose: it can be read, filtered and diffed with ordinary tools rather than needing the Console.

Your home directory is abbreviated to a tilde before anything is written, and any token shaped value is replaced, so the file stays safe to attach to a bug report. It rotates at one megabyte and keeps one older generation, so it cannot grow without limit.

### Added: reading the log from the command line

    redline log                  warnings and errors, newest last
    redline log --tally          grouped by code, most frequent first
    redline log --json --tail 50 structured output
    redline log --level info --days 7

The tally is the useful one when something is wrong repeatedly, because it answers which failure keeps happening rather than which one happened most recently.

### Changed: the silent failures now report themselves

Thirty five kinds of failure are on the record where none were before. Every SQLite error, reported where it is raised rather than at the hundred or so places that discard it, so a failed write to the history store has a cause on file. Every saved state file that will not decode, which is the case that used to reset your alerts, your cadence or your dismissed findings without a word. A config that will not parse, which quietly replaced every preference in it with a default. A Keychain item that will not decode, which reads as signed out and is indistinguishable from an expired grant. A LaunchAgent plist that will not write, which is why the menu bar item would not come back after a restart. Snapshot and sidecar writes, which are what the widget and the command line read.

Two distinctions in there are worth naming, because both used to look identical from the outside. A missing usage sidecar means the feeder was never installed, while a sidecar that will not parse means it is broken. And a missing config is an ordinary first run, while a config that will not parse is about to lose your settings.

Failures that are genuinely routine stay quiet on purpose: a file that is simply absent, a best effort cleanup, a transcript line that carries no usage. Malformed transcript lines are counted per file and reported once, so a change to the transcript format shows up without writing an entry for every record in it. A log full of ordinary events is a log nobody reads.
